--- Maven Key Concepts ---

1
Maven is a build tool that was developed and designed for Java and other languages,
2
and it automates the most common build tasks that need to be done.
3
One of those tasks is dependency management, which is a major component of Maven.
4
Out of that, we get a robust artifact repository system
5
that even tools outside of Maven have adopted.
6
Maven also has a robust plugin framework; actually,
7
nearly all functionality in Maven is provided by a plugin.
8
Also, Maven endorses and solidifies software development best practices
9
by adopting these practices by default. As mentioned before,
10
plugins are a critical component of Maven, since they make up nearly everything in Maven.
11
In addition to providing the default functionality and behaviors in Maven,
12
plugins add more functionalities and features. For example,
13
a plugin may be added to add more goals that can be executed in a Maven build.
14
plugins are also dependencies that need to be downloaded before they are used.
15
Convention over configuration is an approach
16
that can provide useful functionality with little or even no configuration.
17
This is achieved by following prescribed conventions,
18
which are based on best practices and backed up by reasonable defaults.
19
An example of this in Maven would be that Maven expects to find
20
all main Java source code under "src/main/java" folder of your project;
21
you don't have to tell Maven about it, Maven just knows to look there first.
22
With Maven, you generally override the defaults,
23
providing the appropriate configuration settings.
24
Of course, you should only specify the options that are different for your project.
25
A Maven build for a project is defined and controlled by the Project Object Model,
26
AKA POM, which is an XML document that is included with your project files.
27
Normally, it is named "pom.xml". The POM defines all the project Metadata,
28
like the project name, description, and when the project was started,
29
and your project's Maven coordinates.
30
The coordinates is how Maven uniquely identifies the build components,
31
using a combination of a group name, an artifact name, and a version number.
32
Within the POM, the projects declared top level dependencies are defined.
33
All dependencies are also referenced using the same
34
coordinates system mentioned above. The build settings, or other project configuration,
35
is also defined within the POM file; for example, we can specify
36
which version of Java to use, or the final name of the artifact generated.
37
The POM supports some degree of inheritance; Maven comes with a "Super POM"
38
that defines all default settings, which is automatically inherited by all Maven projects.
39
This is how convention over configuration happens in Maven.
40
The project then provides the unique information,
41
and any overrides in that project's POM file.
42
A major advantage of using Maven for building Java projects
43
is the dependency management feature.
44
In Maven, you just declare the main dependency,
45
that is a library or plugin that is needed for your project.
46
Then, Maven will automatically download that dependency
47
and any transitive dependencies along with it.
48
A transitive dependency is basically the dependency of your dependency.
49
Maven will recursively resolve any required dependencies for your project.
50
All dependencies are downloaded from any Maven repositories defined.
51
Dependencies downloaded from the internet are stored locally,
52
in a local Maven repository. You can think of this as a local dependency cache.
53
Maven looks at the local repository first,
54
for any dependencies, before going out to the internet.
55
Finally, dependencies can be bound to a specific scope,
56
which defines when the dependencies are needed.
57
For example, the JUint jar is needed for Testing,
58
but is not needed for deployment to an application server.

--- Maven Lifecycles Explained ---

1

2
Maven has three main groups of actions for executing builds or other tasks.
3
Goals, the lowest level of work in Maven, is the equivalent of a task in Ant.
4
For example, a goal would be to package a Jar file.
5
Often the goal name is a combination of the Maven plugin name,
6
and the goal name within that plugin; for example "compiler: compile",
7
which is the compile goal that is part of the compiler plugin.
8
Phases map one or many goals that are related into a greater lifecycle.
9
For example, the compile phase may call the "compiler:compile" goal for the jar projects.
10
This leads to Lifecycle, which is a collection of related phases.
11
For example, the package phase is combined within
12
the default build lifecycle for jar projects.
13
When you specify a phase within a lifecycle,
14
all phases leading up to that phase are executed.
15
Using the example before, if we call the package phase,
16
the compile, test, and several other phases are executed first.
17
Lifecycles contain phases, and phases map to goals.
18
There are many lifecycles available in Maven, of which
19
many are directed by the type of Maven project being built.
20
For example, a Maven project that builds an enterprise application
21
will have different phases and goals mapped than a project that just builds a jar file.

--- Directory Conventions in Maven ---

1
As part of Maven's convention over configuration,
2
Maven will look at certain project files in specific locations.
3
This is known as the standard directory template.
4
For example, for standard Java projects that produce a Jar file,
5
Maven will look in the main Java source code in "src/main/java",
6
and, any resources, like property files, in "src/main/resources".
7
There are other directory or folder paths Maven will look for;
8
for example, "src/test/java" for Java unit tests
9
and "src/test/resources" for unit test resource files.
10
Maven will look in "src/main/webapp" for Java web application
11
configuration and view files, if your project is a web application.
12
Maven also supports other languages beyond Java;
13
for example, Maven will look in "src/main/groovy" for Groovy language source files.
14
Initially, we'll stick with simple Java projects, but it's good to know
15
that Maven supports a wide variety of languages and technologies.
16
Also, these locations are assumed locations;
17
that is, Maven will look there without any additional configuration.
18
However, if you really need to set an alternative location,
19
you can simply override the defaults by specifying
20
the configuration settings in your project's POM file.
21
However, I highly recommend you stick the Maven defaults as much as possible;
22
this will keep your project's build configuration much simpler.

2

3

4

5
For example plugins often add more goals, that can be executed in a Maven build.
6
Plugins are also dependencies that need to be downloaded.
7
Plugins can do just about anything.
8
Some examples of commonly used plugins would be
9
compiling project source code, running and reporting on unit tests,
10
publishing build artifacts to an artifact repository,
11
deploying your project to a remote server,
12
building and publishing to a documentation server, and many many more.
13
Maven comes with a basic set of plugins to get started.
14
Many common or core plugins are simply known to Maven
15
and are downloaded when needed. Other plugins need to be explicitly mentioned
16
in your project's POM file, in order to let Maven know that you want to use that plugin.
17
In either case, if you want to change the default behavior of a plugin,
18
you can specify the various options within your project's POM file,
19
and the appropriate configuration section.

--- Dependency Overview and Scopes Explained ---

1
In this section, we are giong to dive a bit deeper into dependency management,
2
including finding dependencies and controlling when they are used.
3
One of the main strengths of Maven is dependency management.
4
Simply specify the main dependencies of your project's needs,
5
and Maven will automatically find any additional,
6
or transitive, dependencies also required.
7
Dependencies in Maven are resolved using a Maven repository.
8
By default, Maven comes configured to resolve dependencies from
9
the Maven central repository online;
10
however, additional repositories can be configured.
11
Also, any dependencies will attempt to look locally first,
12
in the private Maven repository that acts much like a cache.
13
When specifying a dependency, we must determine which scope
14
to place the dependency for our project.
15
Maven supports six dependency scopes,
16
although only four are widely used; the six scopes are:
17
compile, runtime, test, provided, system, and import.
18
Compile scope, which is the default scope, signifies the dependency
19
is required for compilation and execution of the project.
20
Compile scope dependencies will be added to any dependent projects;
21
for example, a web module will inherit
22
any compile scope dependencies from a library module.
23
Compile dependencies are included within container projects, like web applications.
24
Runtime scope signifies the dependency is needed
25
during the project's deployment runtime, but isn't needed for compilation.
26
Runtime dependencies are included with the container projects, like web applications.
27
Test scope is for dependencies needed during unit testing.
28
Test dependencies are not needed for compilation of the main source code,
29
nor deployment to the runtime environment.
30
Provided scope tells Maven the dependencies will be provided
31
by the target runtime or deployment system.
32
For example, the Java enterprise libraries, provided by an application server.
33
The rarely used system scope tells Maven about dependencies
34
that are local to the project, or someplace on your system, like in a "lib" folder.
35
However, this approach defeats the point of Maven's dependency system,
36
and should be avoided. The only example of using this scope would be
37
in the rare case of some third-party libraries with excessively restrictive licenses
38
that prevent them being used in a shared repository.
39
In that case, for legal reasons, you might be forced to use
40
system scope for those type of dependencies.
41
Finally, the import scope is rarely used;
42
this scope is only used in specialized cases
43
to import or replace dependencies from other projects.
44
Maven provides the flexibility to handle most of the different ways
45
dependencies are used within their projects.
46
You will most commonly work with compile and test scopes,
47
and then occasionally with provided and runtime.
