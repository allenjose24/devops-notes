--- Why Git? ---

1
2
Git is a decentralized and distributed version control system.
3
While Git is decentralized, most people still choose to use it
4
with a central server to serve as the main repository for a project or team.
5
Because of the distributed nature, Git can scale massively;
6
for example, the creator of Git, Linus Torvalds,
7
wanted to create a version control system that could handle the requirements
8
of the Linux kernel project, which he also created.
9
Today, the Linux kernel project contains over 15 million lines of code,
10
with over 1200 worldwide developers contributing to the project
11
in dozens of active branches. Another key benefit of being distributed
12
is that most operations in Git are local;
13
there are only a few commands that require a network connection.
14
Otherwise, you can work completely disconnected;
15
even preforming comparisons and commits completely off-network.
16
Since most operations are local, Git is very fast with the same operations.
17
Also, Git is free and open source, which also contributes to its popularity.
18
Git has a very active community, and there are many resources available online.
19
Also, it is very easy to find developers that already have experience with Git.
20
Because of all these factors, Git has become the most popular version control system.
21
Git's "de facto" standard status means that Git enjoys
22
wide adoption and integration into other tools used by the development community,
23
including text editors, bug tracking systems, and build servers.

--- Key Git Terminology ---

1
2
Before we dive in, there are just a few concepts you need to know.
3
First, in Git, collections of version controlled files
4
are kept together in a repository. The repository also contains
5
the history of changes and any special configuration.
6
Generally speaking, a repository would contain all the files
7
related to a specific project or application. Next, you need to know about
8
the three local states related to files being managed by Git:
9
the working directory, staging area, and the Git repository or the commit history.
10
The working directory is the directory or folder on your computer
11
that holds all the project or application files.
12
Files within the working directory, may or may not be managed by Git.
13
However, Git is aware of them. Normally, within the working directory
14
is a hidden folder called the ".git" folder that contains the actual git repository.
15
The Git repository manages the Git commit history,
16
that is all the changes that are finalized and permanently part of the Git repository.
17
In-between is the Git staging area, often referred to as the Git index,
18
that is a holding area for queueing up changes for the next commit.
19
Since files in the staging area haven't been committed yet,
20
you can move the files in and out of the staging area
21
without impacting the Git repository, and its history of changes.
22
The three states of Git are specific to the local Git repository,
23
but I like to tack on a fourth state, the remote state. Although the remote repository
24
is just another repository with its own three states internally,
25
conceptually, I think of the remote repository as a fourth state;
26
since it is the last step in the basic Git workflow,
27
and since few people use Git without a corresponding remote repository.
28
The last concept is the master branch.
29
Conceptually, branches work like they do in other source control systems;
30
they are timelines that contain your changes.
31
In Git, branches contain commits; when we start off, Git provides us
32
with a default branch named master. Great, that's all I wanted to cover at this point;
33
I'll cover more concepts later, and while I'm in the demos in the next videos.
